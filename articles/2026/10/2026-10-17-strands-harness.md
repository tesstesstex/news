# Strandsハーネスの仕組みと実務への示唆

- 種別：記事解説（読者指定）
- 原題：AWS、AIエージェントを自作できるツール「Strandsハーネス」をオープンソースで公開　特定のLLMに依存せず入れ替え可能
- 記事URL：<https://www.itmedia.co.jp/news/article/2609/29/2000001837/>
- 掲載元：ITmedia NEWS（Publickey掲載記事を編集・転載）
- 著者：新野淳一
- 原記事の公開日：2026-09-29（掲載ページの日付）
- 収録日：2026-10-17（Asia/Tokyo）

**Strandsハーネスは、LLMに道具・記憶・実行ループを組み合わせる開発基盤です。** エージェントの周辺機能を組み立てた構成から、自分の用途に合わせた開発を始められます。[3][4]

## 3つの要点

- LLMが次の行動を判断し、ハーネスがツールの実行や作業履歴の管理を支えます。
- ファイル操作、シェル、Webアクセス、会話の保存、コンテキスト管理を備え、モデルや部品を交換できます。
- 性能比較は開発元のベンチマーク報告です。業務への適合性、費用、権限設定は導入先で検証する必要があります。

## 記事と一次資料で確認した事実

ITmediaの記事は2026年9月29日公開です。開発元の発表日は同年9月21日で、StrandsハーネスはApache 2.0ライセンスのOSSとして案内されています。記事の公開日、製品の発表日、本稿の収録日は異なります。[1][2]

StrandsはPythonとTypeScriptに対応します。CLIでモデルやツールを選び、構成をコードとして書き出す方法も用意されています。[4]

| 名前 | 役割 |
| --- | --- |
| LLM | 指示やツールの結果を読み、回答や次の行動を選ぶ |
| ハーネス | LLMの呼び出しとツール実行をつなぎ、履歴や状態を管理するソフトウェア |
| Strandsハーネス | ツール・記憶・セッション・コンテキスト管理などを接続した構成 |
| Strands Harness SDK | 実行ループや部品を使い、ハーネスの構成を自分で組むためのSDK |

StrandsハーネスはStrands Harness SDKの上に作られています。組み込みの設定を変更し、用途に応じて部品を置き換えられます。[3]

## 具体例：競合サービスの比較資料を作る

「競合3社の料金と制限を調べ、比較資料をファイルに保存して」と頼む場面を考えます。以下は仕組みを説明するための想定例で、本稿で実行した結果ではありません。

1. LLMが、調べる項目と使うWebツールを選びます。
2. ハーネスがツールを実行し、取得した結果をLLMに渡します。
3. LLMが不足する情報を判断します。追加調査と結果の確認を経て、ファイル操作ツールで資料を保存します。

この判断と実行の繰り返しが**エージェントの実行ループ**です。LLMの出力を道具の実行につなぎ、その結果を次の判断材料にする仕組みが、作業の継続を支えます。[3]

Strandsハーネスにはシェル、ファイルの読み書き・編集、Webアクセスのための機能が用意されています。ただし、Web検索などの対応機能は選ぶプロバイダーにも依存します。[4][7]

## 長い作業を支える「情報の管理」

比較資料を作る途中で大量のページやログを取得すると、LLMが一度に読める情報量の上限に近づきます。Strandsのコンテキスト管理は、過去のやり取りを要約し、大きなツール結果を短い表示と参照先に置き換えます。元の内容は退避先から取得できます。[5]

プロンプトキャッシュは、システム指示やツール定義など、呼び出し間で変わらない部分の再利用を助けます。ハーネスがキャッシュ設定を行うプロバイダーと、サービス側が処理するプロバイダーがあります。[5]

ここからの考察として、調査結果を毎回すべて渡す設計と、必要な部分を取り出す設計では、費用や作業の継続性が変わると考えられます。要約から条件や例外が落ちる可能性もあるため、元の資料を確認する手順が必要です。

「記憶」も役割が分かれます。

| 機能 | 引き継ぐもの |
| --- | --- |
| セッション／チェックポイント | 特定の会話の状態。同じセッションIDを指定して作業を再開する |
| 長期記憶 | 会話をまたいで参照する事実や判断など |

公式資料では、この二つは独立した機能です。長期記憶があることと、特定の作業を途中から再開できることは、異なる性質です。[6]

## 性能評価：実験条件と結論の限界

原記事の性能説明については、開発元ブログを一次資料として確認しました。これは**開発元によるベンチマーク報告**として扱います。[2]

| 項目 | 開発元の発表本文で確認できる内容 |
| --- | --- |
| 比較対象 | 同じClaudeまたはGPTモデルを使うStrandsハーネス、Claude Code、Codexなど |
| 評価範囲 | 6種類のベンチマーク |
| 実行環境 | Amazon EC2上でHarborを使う分散評価 |
| 指標 | ベンチマークのスコアとトークン費用 |
| 発表された結果 | 比較したハーネスに対して、スコアを同程度に保ちながらトークン費用を28%削減したと報告 |

28%は開発元の報告値です。全タスクで同じ割合の削減が得られることや、サーバー費・運用工数を含む総費用の削減率を示す値としては扱えません。[2]

今回確認した発表本文からは、条件ごとの試行回数、統計的な不確実性、全実行の設定を確定できませんでした。推論設定やタイムアウトを含む比較条件の同等性、削減率の集計方法も、本稿では検証していません。

**この結果だけで、自社業務でも他のハーネスを上回るとは結論できません。** モデル、ツール、課題、キャッシュ条件をそろえた検証が必要です。これは評価の適用範囲についての考察です。

## 実務への示唆（解説者の考察・提案）

最初にすることは、**完了条件を決められる業務を一つ選ぶこと**です。競合比較なら「3社の料金に出典がある」「対象プランと調査日が明記されている」などを合格条件にします。

1. **作業の成否を測る。** 選んだ業務で、完了率、誤り、所要時間、トークン費用を記録します。モデルを交換した時も、同じ条件で比べます。
2. **承認とアクセス範囲を設定する。** ファイルの削除や外部への書き込みなど、確認を挟む操作を決めます。
3. **状態の保存先を決める。** 再起動後に必要な会話や記憶を選び、保持期間や利用者間の分離を設計します。

提案の根拠となる仕様も確認しました。モデルはBedrock、Anthropic、OpenAI、Google、Ollama、LiteLLMなどから選べますが、対応機能にはプロバイダーによる違いがあります。[7]

公式資料では、**初期設定ではツール呼び出しに対する承認・ポリシーの介入は設定されていません**。全呼び出しに承認を求める設定や、ポリシーを使う設定が用意されています。[8]

セッションと長期記憶の既定の保存先はローカルファイルです。コンテナなどの一時ストレージに置く場合、インスタンスを越えて状態を保持するには永続ストレージや保存先の設定が必要です。[9]
