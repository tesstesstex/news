# ZOZOTOWNのAIレビュー：指示が守られない前提で権限と検証を設計する

**AIレビューでは、破られると困る制約を権限・検証・前処理で強制する設計が必要です。** ZOZOは、指示が守られない事例を受け、指摘を作るAIとPRへ書き込む処理を分離しています。意味的な判断の誤りは、この構成でも残ります。[1]

## 要点（原記事の主張）

1. **AIによる生成とPRへの書き込みを分ける。** 生成・検証のjobにはPRの読み取り権限を与え、投稿のjobが検証済みの内容を書き込む。
2. **守られない指示を機械処理へ移す。** 旧コードの誤読には読み取り拒否、調査の長期化にはツール呼び出し上限、差分の読み残しには事前の分割を使う。
3. **形式の検証で判断の正しさは保証できない。** 自動承認は適用を限定した試験であり、マージは人が判断する。[1]

## どの制約を強制するのか

原記事の基準は、指示が破られた結果が、レビュアーの判断を経て確定するかどうかです。コメント投稿や承認は、人が読む前に成立します。この部分はAIの従順さに依存させず、権限と検証で制限します。

指摘を採用するか人が判断する場面では、指摘内容の生成をプロンプトに任せられます。ただし、許可する区分や必須項目など、形式で検査できる条件は強制します。人の確認を経る処理でも、失敗が観測され、機械処理で表せる部分は移す方針です。[1]

## 生成・検証・投稿を分ける仕組み

ZOZOはClaude Code GitHub Actionsを使用しています。対象判定の後に動く主要なjobは、次の役割を持ちます。[1]

| job | 役割 | PRに関する権限 |
| --- | --- | --- |
| 生成 | PRを反映したコードを読み、指摘候補のJSONを作る | 読み取り |
| 検証 | JSONの形式、識別情報、差分の行位置、承認の条件を検査する | 読み取り |
| 投稿 | 検証jobが組み立てたartifactを使い、コメントや承認を書き込む | 書き込み |

artifactは、job間で受け渡すファイルです。投稿jobは、AIが作った指摘候補のファイルを読みません。検証jobが用意した投稿内容・掲載先・承認可否を受け取ります。

PRの本文、差分、コメントには、投稿者が指示文を混ぜられます。過去のAIコメントも、次回の実行では同じ入力として扱います。AIの出力にも、その影響が及ぶ前提です。

PR番号とコミットSHAは、生成jobがGitHubから得た値で上書きします。検証jobは、自分で組み立てた識別情報と照合します。投稿jobは投稿・承認の直前にHEADとラベルを再取得し、レビュー時点から変わっていれば実行を見送ります。これにより、別のPRや古いコミットの結果を投稿する経路を制限します。[1]

## 実例から変えた三つの処理

| 起きた問題 | AIから切り離した処理 |
| --- | --- |
| PR変更後のコードを読むはずが、作業ディレクトリにある変更前のコードを参照した | 変更前のコードが置かれた場所への読み取りを権限設定で拒否し、誤参照を検出する監査を残した |
| 調査予算を指示しても検索が続き、ターン数の上限で失敗した | ツール実行前のフックで読み取り・検索の回数を数え、影響範囲ラベルに応じた上限で拒否する |
| 長い差分の表示が途中で切れ、未表示部分を読まずに読了を申告した | 差分を行数と容量で分割し、各断片を一回の読み取りで表示できる大きさにする |

変更後のコード一式は別のディレクトリにあるため、変更前の場所を禁止しても、未変更のファイルを含む調査対象は残ります。検索ツールへの権限規則の適用には限界があるとして、記事では監査を併用しています。

調査予算を超えても、指摘候補の保存は許可します。検証を通ればコメントを投稿できますが、その結果は自動承認など、人の判断を経ずに結果が確定する処理には使いません。ターン数の上限は、異常時の停止手段として残しています。

差分の分割で解消するのは、表示の打ち切りに伴う読み残しです。全断片を読むことは指示に残っており、読了の保証にはなっていません。[1]

## 観測結果と、数字の読み方

変更前コードの誤参照は、監査導入後の約1週間で、完了した実行の**約6%**に見つかりました。これはレビューの誤答率ではありません。作業ディレクトリに存在しない新規追加ファイルなどの誤検知を除いた、参照操作の観測値です。

ターン上限による失敗は、強制前の約1週間で実行の約1割でした。呼び出し回数の制限を導入した後の約3週間は、同じエラーが出ていないと報告しています。調査予算の超過はエラーにしない設計のため、この数字から予算超過がなくなったとは読めません。

記事は総実行数や比較実験を示していません。指摘の採用率、レビュー品質の改善幅、自動承認の試験結果も対象外です。報告の中心は、制約を実装へ移した事例と、その限界です。[1]

## 残る判断とリスク

検証で確かめられるのは、定義した形式・規則との整合性です。指摘の中身や影響範囲ラベルの妥当性は、AIの判断に依存します。正しい形式のJSONでも、必要な指摘が欠ける可能性は残ります。

例えば、AIが「不確か」とした指摘を「修正必須」にする出力は、形式で却下できます。しかし、AIが「確認済み」と申告した内容が正しいかは、その検査では分かりません。PRに混ぜた指示文が判断をゆがめる問題も残ります。

人のレビューにも前提があります。AIの指摘へ注意が集まると、AIが挙げなかった箇所を人も見落とすおそれがあります。記事は、この自動化バイアスと、人が確認した範囲を測定できていない点を課題に挙げています。原記事には自動承認の適用条件や試験結果の記載がなく、安全性を実証した事例としては扱えません。[1]

## 実務への示唆（解説者の提案）

最初にすることは、**レビューAIへ与えている書き込み権限を確認すること**です。

1. 指摘候補を作る処理から、PRへの書き込みを分離する。
2. PR番号・対象コミット・必須項目をAIの外で検証し、不整合時の投稿を止める。
3. 実行ログで誤読・調査超過・読み残しを探し、権限設定や前処理へ移せる制約を選ぶ。
