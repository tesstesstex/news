# AIでコードが増えても、開発成果が増えるとは限らない

- 種別：記事解説（読者指定）
- 原題：AI coding agents generate more code, but not more software
- 原記事URL：<https://arstechnica.com/ai/2026/10/ai-coding-agents-generate-more-code-but-not-more-software/>
- 掲載元：Ars Technica
- 著者：Kyle Orland
- 記事公開日：2026-10-09（掲載ページ表記。表示時刻のタイムゾーンは未確認）
- 収録日：2026-10-17（Asia/Tokyo／日本時間）

**コードを作る能力が高まっても、確認と修正が追いつかなければ、届けられる機能は増えません。** 記事は、AIコーディングエージェントの導入後に生じた、この工程間のずれを紹介しています。[1]

## 3つの要点

- コード行数・コミット・PRは増加しましたが、完了した開発課題や機能の増加は統計的に確認されませんでした。[1]
- PRの提出から取り込みまでの期間が延び、レビューが開発工程の制約になったと著者らは解釈しています。[3]
- 結果は2026年3月までの企業データに基づきます。個々の開発者の効果や、その後のモデルの性能を示すものではありません。[1][2]

## 研究で確認されたこと（事実）

引用元は、ハーバード大学のFiona ChenとJames Strattonによる研究です。Jellyfishのデータ約3億件を使い、AI導入によるコード生産量と開発成果への影響を分けて調べています。[2][3]

コード行数・コミット・PRは、稼働者一人あたりの月間指標です。AIが生成した行だけを数えた値ではありません。表はAIエージェント導入後の推定結果です。[1][2：3.2節]

| 指標 | 推定結果 |
| --- | --- |
| 追加コード行数 | ＋30％ |
| コミット数（変更の保存） | ＋20％ |
| PR数（変更を取り込むためのレビュー申請） | ＋23％ |
| PR提出から取り込みまでの期間 | ＋49％ |
| 完了した課題・機能の数 | 統計的に有意な増加なし |

成果の指標は、Jiraなどで完了した課題（issue）や機能・プロジェクト（epic）の数です。売上を測った値ではありません。[2：3.3節]

**「レビュー期間＋49％」は、PR提出から取り込みまでの経過時間です。** 人がコードを読んでいた作業時間の増加率とは区別します。[2：4.1節]

## 具体例：作成能力と確認能力が違うチーム（架空）

予約システムを作るチームを考えます。同じ規模の変更を週10件作り、10件を確認・テストできるとします。AIによって作成能力が週20件になっても、確認能力が10件のままなら、完了できるのは週10件です。残り10件は確認待ちになります。

予約画面のコードができても、同じ枠への同時申込み、キャンセル時の返金、権限の違いなどは確認が必要です。不整合が見つかれば、修正と再確認が加わります。コードを書く工程の短縮と、利用者に届けるまでの期間の短縮には、違う条件が関わります。

この件数は工程の制約を説明するための仮定です。研究の観測値や効果量ではありません。

## 調査条件と結論の限界

対象は、研究利用に同意したJellyfish顧客718社の2021年1月〜2026年3月の記録です。無作為割付実験ではなく、導入時期の違いを使う差の差分析です。[2：2.1節、3.1節]

推定には、導入がなければ比較する企業群の成果が同じ傾向で推移したという前提があります。企業単位の導入効果であり、全従業員がAIを使った場合の効果ではありません。[2：3.1節]

「有意な増加なし」は、効果ゼロの証明ではありません。コード本文を観測していないため、不具合率の上昇を測った研究としては扱えません。対象企業と観測期間を超える一般化には検証が必要です。[2：2.1節、3.3節]

確認した原稿は2026年8月4日版のJob Market Paperです。学術誌の査読・掲載状況は未確認です。[2：表紙]

## 実務への示唆（解説者の考察）

最初にすることは、**担当機能を一つ選び、実装開始から本番で使えるまでの時間を工程別に記録すること**です。AIへの指示、生成、確認待ち、修正、テストを含めて測ります。

1. **完了を定義する。** 予約機能なら、画面の動作に加えて、同時申込みや返金などの受け入れ条件を決めます。
2. **確認できる単位で変更する。** 画面、予約処理、返金処理を同じPRで変更すると確認範囲が広がります。依存関係を示し、担当者が判断できる大きさに分けます。
3. **待ちと手戻りを比べる。** AI導入前後で、完了件数、確認待ちの期間、修正回数、不具合を比較します。処理能力を超えている工程に、担当者や自動テストを割り当てます。

これらは研究で効果を検証した施策ではありません。予約機能を週10件から増やすには、生成量に加えて、確認を通過できる量を増やす必要があるという考察です。
