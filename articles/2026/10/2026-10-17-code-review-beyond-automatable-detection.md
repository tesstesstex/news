# コードレビューはバグ検出だけではない

- 種別：記事解説（読者指定）
- 原題：There is more to code review than (automatable) detection
- 記事URL：<https://www.adaptivecapacitylabs.com/2026/08/24/there-is-more-to-code-review-than-automatable-detection/>
- 掲載元：Adaptive Capacity Labs
- 著者：John Allspaw
- 記事公開日：2026-08-24（本文に公開時刻・タイムゾーンの記載なし）
- 収録日：2026-10-17（Asia/Tokyo）

**コードレビューには、変更の目的を問い、保守する人の理解を育てる役割があります。** Allspawは、AIによる検出の自動化だけでは、この価値を評価しきれないと論じています。[1]

## 3つの要点

- 不具合を見つける能力から、レビュー全体を代替できるとは結論できません。
- 人の戸惑い、変更の必要性への疑問、対話による相互理解も、著者が挙げるレビューの成果です。
- 引用研究は、削除された文字列を見つける課題での弱点を示します。実務のレビュー能力全体を測った結果とは区別が必要です。[1][3]

## 著者が批判する「置き換え」の論理

批判対象は、Martin Monperrusの論文「The End of Code Review: Coding Agents Supersede Human Inspection」です。レビューを、不具合の検出、規約の遵守、知識の伝達、チームの状況把握に分け、AIが各目的を低コストで達成できると論じています。[2]

Allspawは、この分解で見落とすものを指摘します。欠けた処理への気づき、変更者の経験に応じた注意、リポジトリにない運用事情、承認に伴う責任です。レビューを通じて判断や理解を組み立てる過程を重視しています。[1]

著者は、機能ごとの代替から人の不要化を導く考えを「置き換えの神話」と呼びます。[1] 本解説の読みでは、AIが説明を生成することと、保守する人が説明できることの間にある過程を、どう確かめるかが実務への問いになります。

## 具体例：再試行を増やすPRをどう読むか

以下は、本解説のための**架空の例**です。原記事の事故報告や研究の実験結果ではありません。

注文サービスが外部APIを呼び出す場面を考えます。一時的な失敗に対処するため、再試行回数を1回から3回へ増やすPRが出ました。回数変更のテストは通っています。

このシステムでは、障害時に注文が集中すると、再試行も集中して下流サービスを圧迫する条件があるとします。運用担当者は、前週の障害でその挙動を見ていました。しかし、その経緯はリポジトリに記録されていません。

レビューで担当者が経緯を伝えると、検討対象が変わります。回数を増やす妥当性に加え、待機時間を設けること、再試行を止める条件、異常時の監視を検討できます。

| 確認する観点 | このPRで確かめること |
| --- | --- |
| 目的と範囲 | 失敗率を下げたいのか、障害時の負荷を抑えたいのか。二つの目的を一つの変更に含めてよいか |
| 保守する人の理解 | どの失敗を再試行し、どの条件で停止するかを担当者が説明できるか |
| 運用と引き継ぎ | 前週の障害を踏まえた条件、監視、変更を戻す手順と担当が記録されているか |

この例では、指摘されたバグの件数だけを数えると、変更の前提を修正した価値が見えません。レビューの成果は、小さな修正を加えることに加え、変更を分けることや、採用を見送ることにもなります。これは、本解説の考察です。

## 一次資料で確かめた研究と限界

### 対立論文：人間の必須レビューを減らす提案

Monperrusの論文は、2026-06-11提出のarXiv v1を確認しました。著者は、新たな実証実験を報告せず、既存研究を整理して立場を論じると明記しています。したがって、この論文自体に、人間とAIのレビューを比較する新規実験の条件や結果はありません。[2：I]

原記事の批判を読む際には、対立論文の留保も必要です。同論文は、高リスク変更や新しいアーキテクチャの判断には人間の承認を残します。対話が減るリスクを認め、ペアプログラミングや指導で補う案も示しています。[2：V-A、VII]

本解説では、両者の争点を、人間の判断をどこに置くかという問題として読みます。Monperrusは、必須のPRレビューを減らし、判断を他の工程へ移す構成を提案します。Allspawは、PRを読む過程で生じる理解や調整の価値を重視します。これは主張の比較であり、どちらの体制が優れるかを確定した実験結果ではありません。[1][2]

### AbsenceBench：何を「欠落」として測ったのか

AbsenceBenchは、詩・数列・GitHub PRの4,302例を使う評価です。要素を10%の確率で削除し、原文と削除後の文書をモデルに渡して欠落を答えさせます。平均入力長は約5,000トークンです。[3：2]

14モデルをAPI経由で評価した主要実験では、GitHub PR領域の最高micro F1は**40.0%**でした。対象は思考モードのClaude-3.7-Sonnetです。F1は指摘の適合率と再現率をまとめた指標で、PR全体の正答率とは異なります。[3：3、Table 3]

結論には、次の範囲があります。[3：7]

- 対象は文字列の削除です。要件や設計上の前提の欠落は測っていません。
- 反復間の誤差棒・有意差検定はなく、検討したプロンプトは2種類です。
- 2025年の対象モデルの結果です。人間との優劣や、2026年のツールを使うエージェント全般には一般化できません。

## 実務への示唆（本解説の考察）

**最初にすることは、PRテンプレートに「解決したい問題と、変更しない場合の影響」を追加することです。** 以下は、原記事と研究の限界を踏まえた運用案です。効果が実験で確定した手順ではありません。

1. **目的を確認する。** 変更の理由と採用しなかった案を書く。仕様や範囲の判断が必要な変更は、判断する担当者を決める。
2. **確認した範囲を記録する。** テストやAIの指摘に加え、仕様変更に伴って見直すべきエラー処理、監視、移行手順を列挙する。未確認の項目は未確認と記す。
3. **保守する人の理解を確かめる。** 担当者が失敗時の挙動と変更を戻す条件を説明する。説明がつながらない箇所は、実装・文書・前提のどこを直すか話し合う。

再試行の例なら、回数のテストに加え、「負荷が増えた場合に何が起きるか」「どの条件で戻すか」を説明できる状態を目指します。AIの検出結果と、人が運用を引き継ぐための確認を、承認の根拠に残す運用です。
