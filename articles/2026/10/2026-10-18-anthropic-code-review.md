# Anthropicのコードレビュー：人の確認時間を減らす条件

- 種別：記事解説（読者指定）
- 原題：How the Claude Code team does code review
- URL：<https://claude.dev/blog/solving-code-review-at-anthropic/>
- 掲載元：claude.dev Blog（Anthropic）
- 著者：Addy Osmani、Morgan Westlee Lunt、Qing Wang
- 公開日：2026-10-15（原記事の表示日）
- 収録日：2026-10-18（Asia/Tokyo）

**Claude Codeチームは、レビューと障害対応に使う人の時間を減らす工程を組んでいます。**[1]

## 3つの要点

- 変更のリスクに応じて人の承認を求める。[1]
- 誤検出とレビューの反復を抑える。[1][4]
- サービスのレビューと、承認・CIの制御を分けて考える。[2]

## 記事が報告する変化

Claude Codeのコードベースでは、2026年6月から9月にマージされたPR数が2倍超になり、取り消しが必要になった割合は40％超低下したと報告しています。[1]

これは社内の前後比較です。元の取り消し率、PR件数の実数、比較群は本文に示されていません。**40パーセントポイントの低下や、障害件数の40％削減を意味しません。** 変更の大きさや工程の変化を含むため、この数値からAIレビュー単独の因果効果は判定できません。

## 人の承認をどこに残すか

自動レビューとセキュリティ検査、CIを土台に、人の承認要件を分けています。[1]

| 変更のリスク | 必要な人の承認 |
| --- | --- |
| 低 | 自動検査の通過後は不要となる経路がある |
| 中 | 1人 |
| 高 | 2人 |

承認を減らす経路は信頼済みの作者が対象です。指定された機微な領域やCIワークフローは人の確認を要し、AIの承認で人の枠は埋められません。AIに変更を指示した人も承認者に数えます。[1]

ここからは解説者の考察です。この分担では、レビュアーに頼む仕事を定義する必要があります。「変更を読んでほしい」だけでは、業務上の目的、設計上の制約、障害時の影響のうち、何を判断する役割なのかが曖昧になります。

差分が短くても、予約を確定する条件の変更には業務判断が含まれます。テストの合格は、テストが確認した条件で動いた証拠です。その条件が業務に合っているかは、仕様や利用状況との照合が必要です。

## レビューを終わらせる設計

同チームは、3巡後に方針の見直しを求める運用を導入しました。数巡後の再レビューは差分を中心にし、既出の指摘の再投稿を防ぎます。[1]

解説者の考察として、指摘の数は品質の指標として不足します。命名の提案を受けるたびにAIが修正し、別のAIが別案を出すなら、コミットと確認の費用が増えます。検出すべき不具合と、好みの提案を分ける必要があります。

「どの入力で、期待と異なる何が起きるか」を指摘の条件にすると、修正の要否を判断する材料になります。根拠を示せない提案への対応と、再現する不具合の修正には、異なる優先度を付けられます。

## 市販のCode Reviewが担う範囲

Code Reviewは2026-10-15にTeam・Enterprise向けの一般提供へ移りました。[3] 公式資料では、複数のエージェントが差分と周辺コードを調べ、候補を検証し、重複の除去と重要度の判定を経てコメントを投稿します。[2]

サービスはPRを承認・ブロックせず、チェックも失敗として終了しません。レビュー中にコードのビルドや実行は行いません。[2] **社内運用の承認制御やCIは、サービスの導入に加えて設計する部分です。** 原記事の承認表を、製品の初期設定として扱うことはできません。

レビューの調整には、プロジェクトの前提を置く`CLAUDE.md`と、レビュー用の`REVIEW.md`を使います。公式資料は、指摘の重要度、除外対象、根拠の要求などを`REVIEW.md`で指定できると説明しています。[4]

注意する条件があります。サービスは両ファイルを読みますが、ローカルの`/code-review`は`REVIEW.md`を読みません。両方に必要な指示は`CLAUDE.md`に置きます。サービスが読む`REVIEW.md`はPR内の変更版ではなく、ベースまたはデフォルトブランチの版です。指摘の抑制などには、保護されたデフォルトブランチ上のルートファイルという条件もあります。[4]

## 架空の例：営業時間の表示と予約の確定

以下は、解説者が作った例です。Anthropicでの実例ではありません。

予約サイトで、営業時間の表示を直すPRと、予約確定の条件を変えるPRを考えます。前者では表示結果と元の営業時間を照合します。後者では、在庫の競合、キャンセルとの関係、確定後の通知を含む確認が必要になります。

両方に同じ承認人数を割り当てると、表示修正の待ち時間と、予約処理に必要な判断を同じ規則で扱うことになります。変更で失うものを挙げれば、必要な証拠と担当者を決める手掛かりになります。

## 実務で試すこと（解説者の提案）

最初にすることは、**直近のPRを一つ選び、人が何を確かめたかを書き出すこと**です。待ち時間が長い理由と、検査が足りない理由を区別できます。

1. **確認対象を決める。** 不具合の検出、業務判断、設計判断に分け、必要な担当者と証拠を書きます。実行できる条件はテストやCIへ移します。
2. **一つのリポジトリで試す。** AIの指摘を、修正したもの、誤りだったもの、意図した動作だったものに分けます。同じ指摘の反復も記録します。
3. **人の総作業時間で比べる。** レビュー作業と待ち時間を分け、障害対応の時間、変更数、取り消し・障害の割合を並べます。承認人数の変更は、この結果から判断します。

これらは本解説の提案です。原記事が効果を検証した導入手順や、どの組織でも承認を減らせるという保証を表すものではありません。
