# Learn Claude Codeの読み方：ループ・知識・権限・完了条件を組み立てる

**Learn Claude Codeは、モデルとツールの往復を核に、知識・権限・記憶・終了判定を組み立てる学習用教材です。** 現行版は17章です。shareAI-labの独立した実装を読み、エージェントを動かす周辺の仕組みである「ハーネス」を学べます。[1]

## 要点

1. **モデルの要求を実行し、結果を返すループが土台。** ツール呼び出しの有無に応じて、実行の継続と一回の応答の終了を分けます。[2][3]
2. **知識と実行権限を別の仕組みにする。** Skillsは必要な手順をモデルへ渡し、権限チェックはツールを動かす前に置きます。[4][5][6]
3. **作業の終了には、確認できる完了条件を使う。** 最終章では別のモデル呼び出しが履歴中の証拠を評価します。検証そのものは実行ツールが担います。[7][8]

## 教材の中心：モデルが選び、ハーネスが実行する

READMEは、推論や行動選択をモデルの能力、ツール・知識・観測結果・権限をモデルへ接続する仕組みをハーネスとして説明しています。[1]

この分担をコードで見ると、役割が分かります。s01のモデルは、実行したいコマンドを構造化された `tool_use` として要求します。Python側がそのコマンドを実行し、結果を会話へ追加します。[2][3]

処理の順序は次のとおりです。

1. 利用者の依頼、会話履歴、ツールの定義をモデルへ送る。
2. 応答にツール呼び出しがあれば実行し、呼び出しIDに対応する結果を履歴へ戻す。
3. 更新した履歴でモデルを呼ぶ。呼び出すツールがなくなると、この章のループは終了する。[2][3]

コードから確認できるのは、モデルが要求を返し、実行側が操作と結果の受け渡しを担う分担です。Claude Code製品の内部実装との一致を、この教材だけで判断することはできません。

## Skills：モデルへ渡す知識を選べるようにする

s07では、起動時に `skills/*/SKILL.md` を走査します。名前と説明から一覧を作り、system promptへ入れます。モデルが `load_skill(name)` を呼ぶと、対応する `SKILL.md` の全文がツールの結果として履歴へ入ります。[5][6]

| 段階 | モデルへ渡る情報 |
| --- | --- |
| 起動時 | 利用できるSkillの名前と説明 |
| `load_skill` の呼び出し後 | 選んだSkillの全文 |

実装は起動時にファイル全文をメモリへ保持しています。**必要時まで遅らせているのは、全文をモデルの入力へ載せる時点です。** ファイルを読む時点と、モデルが内容を受け取る時点を分けて読むと、仕組みを追えます。[6]

付属例は、エージェント構築、コードレビュー、MCP構築、PDF処理です。[5] この章から得られる設計上の示唆は、すべての作業手順を初期入力へ詰める代わりに、選択用の説明と手順本文を分けることです。これは解説者の考察です。呼び出し後の本文も履歴を使うため、読み込みだけで文脈の問題が解消するとはいえません。

## 権限：手順を渡す場所と、操作を許可する場所

s03では、ツール実行の前に権限判定を挟みます。禁止条件に一致すれば拒否し、確認対象の操作なら利用者へ承認を求めます。それ以外は実行へ進みます。[4]

Skillに作業の規約を書いても、その規約の存在だけでは操作を制限できません。実行側が、どのパスや操作を許すかを判定する必要があります。これは教材の役割分担から得られる解説者の考察です。

s03の説明は、禁止リストを単純な文字列照合と位置付け、完全なセキュリティ境界ではないと明記しています。[4] 実運用へ持ち込む際は、実行環境の隔離やアクセス範囲を含め、必要な境界を別途設計する対象です。

## Goal Loop：「応答が終わる」と「仕事が終わる」を分ける

s01の終了条件は、モデルがツールを要求しなくなることです。s17は、その終了候補の時点で完了条件を評価する仕組みを加えます。[2][7]

評価側は、作業するモデルとは別のAPI呼び出しです。条件、会話、履歴へ戻ったツール結果を読み、達成したか、不足があるか、完了が不可能かを返します。ツールを持たず、ファイルを開いたりテストを再実行したりはしません。[7][8]

コードでは、シェルの結果に終了コードを付けて履歴へ返します。評価側は、その記録を判断材料にします。判定の役割が分かれていても、異なるモデルを使うことは必須ではありません。設定がなければ、評価側も作業側と同じモデルIDを使います。[8]

未完了なら理由を同じ会話へ追加し、作業を続けます。評価呼び出しの失敗や継続上限では、未達成の目標を保持して制御を返します。バックグラウンドの作業が残る場合は、結果を待ってから判断します。[7][8]

**別のモデル呼び出しによる判定と、成果物の検査を区別することが要点です。** 評価側が読める証拠が欠ければ、条件を確かめる材料も欠けます。モデルによる評価の誤りがなくなることを、この実装が保証するわけではありません。

## 架空の応用例：社内スライドの作成

以下は、s07の知識読み込みとs17の終了判定を同じホストへ接続する場合の、解説者による設計案です。

「承認済みの数値から8枚の報告資料を作る」という依頼を考えます。

| 役割 | 設計するもの |
| --- | --- |
| Skill | 会社の配色、表記、出典の記載方法をまとめた `SKILL.md` |
| 実行ツール | PPTXを生成し、ページ画像へ変換する処理 |
| 権限 | 参照する資料と、書き込みを許す保存先 |
| 完了条件 | PPTXが開ける、8枚ある、指定の出典がある、ページ画像の確認結果が記録されている |

ここでは、Skillが書式や手順を伝え、実行ツールがファイルを作ります。ページ画像の内容や見た目は、確認する工程で判断します。その結果を履歴へ戻すと、終了判定で参照できるようになります。

「スライドを作成しました」という文章だけで終了させないために、生成・検査・結果の記録を分ける設計です。このスライド作成の流れは、教材の付属実装を実行した結果ではありません。

## 読み始め方と根拠の範囲

最初は、**s01で依頼、ツール要求、実行結果の往復を追うこと**を勧めます。

1. s01とs02で、モデルへの入力と、実行側が返す結果を確認する。
2. s03とs07で、権限の判定と知識の受け渡しを確認する。
3. s17で、完了条件に必要な証拠と、続行・停止の分岐を確認する。

これは解説者の読解手順です。履歴の圧縮、記憶、チーム実行などは、目的に応じて各章へ進めます。

READMEには、Agencyの由来や他の開発方式に対する強い主張があります。本稿では著者の立場として扱っています。歴史的なゲームAIの成績から、現行の業務エージェントの優劣や、特定の実装方式の普遍的な有効性を結論付けていません。

確認したのは、指定README全文、s01・s03・s07・s17の日本語説明と、該当するソースコードです。APIを使う実行試験、学習効果の測定、本番環境での安全性評価は行っていません。各章の機構が存在することと、それが要求に対して十分に機能することを分けて読んでいます。
