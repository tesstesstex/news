# コーディングAIの性能を左右するハーネス設計

- 種別：記事解説（読者指定の論文）
- 原題：An Empirical Study of Harness Design for Coding Agents
- 記事URL：<https://arxiv.org/pdf/2609.20804>
- 掲載元：arXiv
- 著者：Run-Ze Fanほか
- 公開日：2026-09-17（arXiv v1の初回投稿日表記）
- 投稿履歴の時刻：2026-09-17 17:58:07 UTC（2026-09-18 02:58:07 JST）
- 収録日：2026-10-17（Asia/Tokyo）
- 読解対象：arXiv:2609.20804v1。公開日と投稿履歴は書誌ページで確認。[1]

**コーディングAIを改善するには、失敗が起きる段階に合った機能を選ぶ必要があります。** これが本稿の実務上の読み取りです。ハーネスとは、モデルに渡す履歴・計画と、使える操作を管理する周辺ソフトウェアです。[1]

## 3つの要点（論文の報告）

- 履歴管理は、入力上限による作業の途中終了を防ぐ。効果は入力枠が狭い条件で増える。
- 計画は、能力の低いモデルの編集到達を支え、能力の高いモデルの確認の反復を減らす。
- 専用ツールとbashの優劣は、シェル操作の能力と課題によって変わる。[1]

## 比較した条件

論文は、モデルを固定してハーネスの構成要素を変える比較を行っています。[1、3.1節]

| 項目 | 条件 |
| --- | --- |
| モデル | Nemotron-3の30B・120B・550B、Mistral-Medium-3.5-128B |
| 入力枠 | 32k・64k・96k・128kトークン |
| 課題 | SWE-Bench Verifiedの500件、Terminal-Bench 2.1の89件 |
| 操作の比較 | 専用ツール群＋bashと、bashのみ。計画等の補助ツールは両構成に残す |
| 評価 | 課題の成功率と、使用トークンを論文採用のAPI単価で換算した平均費用 |

SWE-bench Verifiedは、人が選別したGitHubの課題を使う評価です。Terminal-Bench 2.1は、コマンドラインで作業する課題の評価です。課題数と評価の位置づけは、各ベンチマークの一次資料でも確認しました。[2][3] 表の費用は、実測したGPU運用費を意味しません。[1、3.1節]

## 履歴を残すことと、作業を続けられること

**論文の事実：** T4は古いツール出力を省略し、それで足りなければ履歴を要約します。管理方式間の集計では費用が低い構成でした。省略した出力を呼び戻す機能には、一貫した成功率向上が確認されませんでした。[1、2.3節・3.2節]

Nemotron-3 550Bを使い、SWE-Bench Verifiedを32kの入力枠で解いた結果は次のとおりです。管理なしのT0は、入力上限を超えると終了する仕様です。[1、表3]

| 履歴管理 | 成功率 |
| --- | --- |
| T0：追加の履歴管理なし | 6.4% |
| T4：省略・再取得・要約 | 55.6% |

**説明用の例（架空）：** 予約システムの二重予約を直すAIが、検索結果やテストログを読み続けているとします。原因の候補を見つけても、編集前に履歴の上限で終了すれば修正は完成しません。

この例なら、古い検索出力を省略し、「問題のファイル」「試した修正」「残るエラー」を短い記録にする設計を考えられます。ただし、これは仕組みを理解するための例です。論文が予約システムでこの記録形式を検証したわけではありません。

**解説者の考察：** 上の比較を「要約すれば推論能力が上がる」と読むことはできません。途中で終了する条件を減らすことと、原因を見抜く能力を高めることは、分けて評価する必要があります。

## 計画は、開始と終了の判断にも関わる

**論文の事実：** 比較対象の計画は、進捗を更新し、各ターンの入力に渡す作業表です。能力の低いモデルでは編集前の終了を減らし、能力の高いモデルでは編集後の検証を短くする傾向が報告されています。費用削減に成功率の微減を伴う条件もありました。[1、2.1節・3.2節・4節]

**説明用の例（架空）：** 二重予約の修正で、「競合を再現する」「確定処理を直す」「同時リクエストのテストを通す」という作業表を用意します。調査だけで終わるAIには、未完了の編集が残っていることを示せます。確認を繰り返すAIには、完了条件を照合する材料を渡せます。

**解説者の考察：** 「計画を書かせる」という指示の有無だけでは、使われ方を判断できません。計画が更新されているか、未完了の仕事を残して終了していないか、確認を繰り返していないかを見る必要があります。

## 操作の選択肢は、使いこなせるかで評価する

**論文の事実：** Mistralは、SWE-Bench Verifiedでは専用ツールのある構成、Terminal-Benchではbashだけの操作構成で成功率が高くなりました。[1、3.2節・表3・表4]

**説明用の例（架空）：** ファイルを探し、対象行を読み、編集結果を確認する仕事は、専用ツールに分けて依頼できます。シェルを使う場合は、検索と表示を一つのコマンドにまとめる設計も考えられます。呼び出し回数が減っても、コマンドの誤りや出力の見落としが増えるなら改善とはいえません。

**解説者の考察：** ツール数の少なさを目的にせず、利用するモデルが操作を成功させられるかを測るべきです。この比較だけを根拠に、権限制御や検証まで削る判断はできません。

## 結論の限界

各設定は課題ごとに1回の実行です。計画と操作ツールの比較はT4・128kに限られます。操作構成の変更には、指示文・ファイル状態管理・編集後の自動診断の変更も含まれます。したがって、ツール数だけの効果を切り分けた実験ではありません。[1、Limitations]

Terminal-Benchは89件で、統計的な有意差に達しない比較もあります。対象モデルとソフトウェア開発課題を超えて、同じ効果が出るとは結論できません。[1、Limitations]

## 実務への示唆（解説者の提案）

最初にすることは、**失敗した実行ログを一件選び、どの段階で止まったかを確認すること**です。

1. 入力上限、編集前の終了、操作エラー、確認の反復のうち、どの問題が起きたかを記録します。
2. 対応する履歴管理・計画・操作インターフェースを一つ変更します。同じモデルと課題で比較します。
3. 成功率、途中終了の理由、トークン量、所要時間を照合します。費用だけが下がった場合は、仕事を終える前に停止していないか確認します。

これは導入時の評価手順の提案です。論文で検証した運用手順ではありません。予約修正なら、「変更したか」に加え、「同時リクエストで二重予約が起きないか」を完了条件に含めます。
