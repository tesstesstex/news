# 検証の記録を改善へ返す：PRの証拠と、検証できない理由を残す

**実行した検証と、できなかった検証をPRごとに記録し、その不足を次の改善へ返す提案です。** テストを追加するだけでなく、ハーネスや実行環境が検証を続けられる状態を育てます。[1]

## 要点

1. PRをレビュー可能な状態へ進める前に、検証の記録を用意する。[1]
2. 検証に詰まった理由やレビューの採否を調べ、手順・道具・指示を更新する。[1]
3. 記録が作られる前に落ちる基盤の問題は、別のfeedback経路で拾う。[1]

## 検証をしたか、後から確かめられるようにする

記事では、verifications/{PR番号}.mdへ、確認した手順と未確認の項目を残す運用を紹介しています。記録があることで、行うべき確認が省かれた場合にも、それが表面へ出ます。[1]

以下は解説者の例です。

| 状態 | 記録する内容 |
| --- | --- |
| 実行して成功 | コマンド、対象、結果 |
| 実行して失敗 | 失敗した条件と、残る問題 |
| 未実行 | 未確認の範囲と理由 |
| 実行基盤で中断 | 検証へ到達できなかった段階 |

「確認した」と書くことだけで、成功の証拠が得られるわけではありません。外から確認できる結果へ結び付けるのが、この表の意図です。

## 不足の記録が、次の改善の材料になる

著者は、検証ファイル、AIレビューの指摘と採否を定期的に見直し、改善のPRや課題を作る流れを紹介しています。矛盾する指示の重複を減らす方針もあります。[1]

検証が失敗した理由を残せば、次の担当者が同じ準備からやり直す負担を減らせます。ただし、記録を生成する前に実行環境が落ちる場合には、その記録だけを集めても問題を見落とします。feedbackの経路を補う理由がここにあります。[1]

## 運用報告としての限界

Imprintで導入している途中の経験を述べた記事です。改善用のPRが生成されることは、品質がその件数分向上したことを意味しません。

共通の手順を集中管理する利点と、各チームで探索する余地の両方が論点です。すべての組織で同じ集中管理が最適と実証したものではありません。紹介されたスキルや自動実行を、本稿では導入・実行していません。
